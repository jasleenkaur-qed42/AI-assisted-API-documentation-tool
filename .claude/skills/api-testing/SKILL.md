# API Testing

## Goal

Add executable tests to the Postman collection generated by API documentation.

## Workflow

1. Read the existing Postman collection.
2. Do not recreate the collection.
3. Analyze the API implementation using `api-analyst`.
4. Identify testable success and error behavior.
5. Add Postman test scripts to the existing requests.
6. Validate the collection JSON.

## Test Coverage

Where supported by the implementation, cover:

* successful responses
* status codes
* response structure
* required fields
* validation errors
* invalid IDs
* missing resources
* duplicate values

Do not invent expected behavior.

Mark unclear behavior:

`Behavior needs verification`

## Test Design

Tests should verify observable API behavior.

Where appropriate, assert:

HTTP status code
response body structure
required response fields
expected field values
error response structure
important business or validation rules

Do not make tests unnecessarily implementation-specific.

Do not assert internal implementation details that are not part of the API contract.

## Rules

* Modify only the Postman collection.
* Do not modify application source.
* Do not install packages.
* Do not commit or push.
* Do not modify routes, controllers, services, database code, or configuration.
* Do not create a new Postman collection when the expected collection is missing.
* Do not weaken or remove existing tests simply to make them pass.
* Do not invent expected API behavior.

## Output

Report:

collection updated
endpoints with tests added
test cases added
collection path
uncertainties
any missing or unsupported test scenarios

Do not start another workflow stage yourself. Return the result to the orchestrator.
